# 技術選定

- フロントエンド: Next.js
- バックエンド: FastAPI
- DB: PostgreSQL (Supabase)
- 認証: Supabase Auth

## バックエンド選定

### 候補

- Node.js + Express
- Ruby on Rails
- FastAPI(Python)

### 評価観点

- 個人開発のため、開発規模は小さい
- SNS指向のサービスである。
- コストはなるべく抑えたいです
- Next.jsとNextAuth.jsをすでに採用
- 学習歴はRailsとFastAPI

### メリット・デメリット

- Ruby on Rails
　結論：早くリリースして、成功したら作り直す戦略に最適。
  - メリット：
    - フレームワークの特性上、開発が早い
    - SNS機能がライブラリとして豊富
    - 学習歴がある
  - デメリット：
    - 他に比べ同時接続により処理速度が遅くなる
      → 個人開発のため、成功するかどうか不明。先の事を考えすぎ感がある。
    - メモリ消費が大きいため、コストが高くなる可能性がある
    - 非同期処理、リアルタイム機能の実装が複雑
    - スケーリングが難しい
    　→ ユーザ数が増えた場合は、別の技術に移行する必要がある

- FastAPI
  結論：少し時間をかけてでも、将来のスケールに備えたい場合に最適。
  - メリット：
    - 高速な処理性能、コスト効率
    - Next.jsとの親和性が高い。型定義自動生成により、フロントエンドとの連携が容易。
    - 自動ドキュメント生成。AIでの開発相性〇
    - 学習歴がある
  - デメリット：
    - 実装に時間がかかる可能性がある。ライブラリがRailsに比べて少ない。
    - 管理画面の実装がRailsに比べて手間がかかる
    　→ Next.jsの管理画面を利用することで多少は解決可能

- Node.js + Express
  結論：Next.jsとNextAuth.jsをすでに採用しているため、全体最適の観点で最適。
  - メリット：
    - Next.jsとの親和性が高い
    - 非同期処理が得意で、リアルタイム機能の実装が容易
  - デメリット：
    - CPU負荷が高くなる可能性がある
    - 学習歴がない
    - TSの設定が大変

## DB選定

### 候補

- PostgreSQL
- MySQL
- MongoDB

### 評価観点

- 実装機能に最適なデータモデルをサポートしていること
- コストを抑えられること
- Next.jsとFastAPIとの親和性
- ランキング機能, 地図表示機能との親和性

### メリット・デメリット

- PostgreSQL
  結論：
  - メリット：
  　- PostGISにより地図表示機能との親和性が高い
  　- Supabaseにより無料プランあり

- MySQL
  結論：
  - メリット：
    - PostgreSQLより若干高速
  - デメリット：
    - PostGISのような地理空間拡張がないため、地図表示機能の実装が難しい

- MongoDB
  結論：
  - メリット：
    - 柔軟なスキーマでデータモデルを自由に設計できる
    - 地理空間クエリに最適
  - デメリット：
    - FastAPIとの親和性が低い
    - ACID保障が弱いため、フォロー機能やランキング機能の実装が難しい

## 認証選定

### 候補

- NextAuth.js
- Auth0
- Firebase Authentication
- Supabase Auth

### 評価観点

- SSOでログイン可
- ゲストユーザ、ログインユーザ、プレミアムユーザ(サブスク)で機能制御
- ログインユーザは投稿・いいね・フォロー・神社登録・御朱印登録を行う
- ↑のため、DBに登録が必要
- モバイルアプリとの連携

### メリット・デメリット

- NextAuth.js
  結論：カスタマイズ性は高いが、実装工数とモバイル対応で劣る。
  - メリット：
    - 完全なセルフホスト、ベンダーロックインなし
    - あらゆるOAuthプロバイダーに対応、カスタムプロバイダーも簡単に追加可能
    - 認証フローを完全に制御可能、セッションデータのカスタマイズが自由
    - 追加の認証サービス料金が不要
  - デメリット：
    - DBとの連携にPrisma/Drizzle Adapterの設定が必要、auth専用テーブルの管理が煩雑
    - FastAPI側でJWT検証ロジックを自前実装する必要があり工数増
    - モバイルアプリでは別途認証実装が必要（API経由での独自実装）
    - ゲストユーザーの実装が複雑、匿名認証の標準機能なし
- Supabase Auth
  結論：最適解。DBとの統合性、コスト、機能のバランスが最も優れている。
  - メリット：
    - 認証DBと業務DBが同一PostgreSQL内で直接JOIN可能（auth.usersテーブル）
    - 5万MAUまで無料、DB料金（$25/月）に含まれるため追加コスト不要
    - 匿名認証でゲストユーザー対応、RLSでロール別アクセス制御が宣言的に実装可能
    - React Native SDKでモバイル対応完備、Web/モバイルで同一の認証フロー
    - Google等の主要プロバイダー対応、リアルタイム機能で権限変更を即座に反映
  - デメリット：
    - Supabaseへのベンダーロックイン（ただしPostgreSQL標準なので移行は可能）
- Auth0
  結論：エンタープライズ向けで高機能だが、個人開発にはオーバースペックで高額
  - メリット：
    - SAML/OIDC等のエンタープライズSSOに完全対応
    - Web/モバイル向けSDKが充実、実装が最も簡単
    - ユーザー管理UIが標準で提供される
  - デメリット：
    - ユーザーデータが外部管理となりDBとの統合が複雑（UserIDの二重管理）
    - ロール管理が独自仕様でPostgreSQLとの連携が煩雑
- Firebase Authentication
  結論：モバイルファーストだが、PostgreSQLメインのアーキテクチャとは相性が悪い
  - メリット：
    - 5万MAUまで完全無料、コスト面では優秀
    - モバイルSDK（iOS/Android）が最も充実、プッシュ通知との統合も簡単
    - Googleのインフラで高い可用性とスケーラビリティ
  - デメリット：
    - FirebaseのUIDとPostgreSQLのuser_idの二重管理が必要
    - FastAPI側でAdmin SDKを使った検証が必要でレイテンシが増加
